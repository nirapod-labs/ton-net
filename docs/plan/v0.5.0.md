# ton-net v0.5.0: the write path

**Status:** planned. No code in this stage begins before `NET-ADR-013` is accepted.
**Version at planning time:** `0.4.2` (`Cargo.toml:27`).
**Verification epoch at planning time:** `2` (`crates/ton-net/src/lib.rs:117`).

Every claim about this tree below carries a `file:line` anchor and states the scope it was checked at, except where the claim is about the release sequence itself, which is named rather than anchored. Anchors were taken at `e5a6a80`, working tree clean. Facts that live outside this repository, whether about TON contracts, liteserver internals, TL constructor ids, or what other implementations do, are marked external, listed in section 10, and not asserted here; each one is bound to a gate that turns it into a checked fact before the code that depends on it ships.

---

## 1. What v0.5.0 delivers

**The write path, as one vertical slice: build an external message, sign it outside this library, send it, and read the result back in a proven account read.**

`NET-ADR-001` fixes the target:

> "the write path, a trust-minimized read-and-send client able to back a wallet end to end, is the floor the project holds itself to" (`docs/adr/NET-ADR-001-purpose-and-priorities.md:73-76`)

and fixes what makes it observable:

> "The floor is observable: the cell engine ships every gate green, and the write path sends a real transfer observed in a proven account read." (`docs/adr/NET-ADR-001-purpose-and-priorities.md:119-120`)

That second sentence names a **read** as the proof. The proven read already exists: `Client::account` answers `Verified<Account>` (`crates/ton-net/src/client.rs:261`), and `Verified::new` is `pub(crate)` with one call site (`crates/ton-net/src/verified.rs:41`, called at `crates/ton-net/src/client.rs:384`). So the floor becomes observable the moment the send half can put one external message on the wire and the confirmation half can read the consequence back. That is what v0.5.0 builds.

Shipped capability:

- External message construction: `StateInit`, `CommonMsgInfo`, `ext_in_msg_info$10`, and the TEP-467 normalized external-in hash.
- One wallet family, V4R2, simple send only (`op = 0`).
- `liteServer.sendMessage` over the existing single-channel ADNL transport.
- Confirmation as a proven account read: a positive verdict when the signed seqno is consumed, and a **proven negative** verdict when the signed deadline has passed on the chain's own clock and the seqno never moved.
- A signer seam that is a value boundary: sixty-four bytes cross inward, and nothing crosses outward.

The scale debt from `NET-ADR-012` decisions 1 and 2 rides alongside as **side work**, in section 8. It is not the release, it lands in `crates/ton-net-cell/` only, and it is ordered so it never blocks the write path.

## 2. The custody position, stated first

This is a non-custodial library. The line is the product, so it is stated before the work and it is held by things a compiler or a command checks, not by a convention.

### 2.1 The line

`NET-ADR-003` states it twice, and the two statements are not identical:

> "Its first contact with key material is a signer seam, where the caller supplies the signing operation and the library never sees a private key or a seed." (`docs/adr/NET-ADR-003-scope-and-write-path.md:69-71`, decision 2)

> "it enters through a signer seam: the caller supplies the signing operation, and the library never holds or sees a private key or a seed. Constructing and broadcasting an external message is not custody. Signing with a key the library holds would be, and the library does not do that." (`docs/adr/NET-ADR-003-scope-and-write-path.md:133-137`, the custody section)

The operative decision clause carries the weaker predicate. The custody section carries the stronger one, and so does the release sequence. Reconciling them is question Q2 in section 4.

**Under the v0.5.0 design both sentences are true verbatim, because no seed and no private key enters any crate in this workspace at any point.**

### 2.2 What holds it, mechanically

Four mechanisms. Each names the scope it covers, and each is followed by what it does not cover.

**The absent dependency edge.** This is the mechanism `NET-ADR-011` already uses for the trust barrier:

> "the enforcement is the absent dependency edge rather than anyone's diligence" (`docs/adr/NET-ADR-011-identity-and-trust.md:189-193`)

Verified at `e5a6a80` by reading both manifests:

- `crates/ton-net-block/Cargo.toml` declares exactly `ton-net-cell`, `ton-net-tl`, `curve25519-dalek`, `sha2`, `thiserror` under `[dependencies]`. No `tokio`, no `getrandom`, no `ton-net-adnl`, no `ton-net-lite`. **The crate that builds a signable body therefore has no socket, no clock, and no randomness source.** It cannot send what it built, cannot draw entropy to generate a key, and cannot timestamp.
- `crates/ton-net-lite/Cargo.toml` declares exactly `ton-net-tl`, `ton-net-adnl`, `thiserror`. No `ton-net-cell`. **The crate that sends cannot name a `Cell`**, so it cannot build or inspect a message; it moves opaque bytes.

The two halves of the write path sit in crates blind to each other and meet only in the facade. Gate G2 asserts each absent edge by name off `cargo metadata`, and asserts a present edge in the same reading, so an assertion whose reading matches nothing cannot pass for free. That two-reading discipline is copied from `scripts/check-default-deps.mjs`.

**Scope:** those two manifests at `e5a6a80`. This does not say "no key can reach the library." No dependency edge prevents a `&[u8; 32]` parameter from being added to any function in any crate. What it prevents is derivation, entropy draw, and network reach from the crate that composes signable bytes.

**The chokepoint constructor.** Design, gated by G1. `Signed` has private fields and exactly one function in the workspace that returns it: `Unsigned::into_signed`. `Unsigned` likewise has exactly one: `WalletV4R2::transfer`. This is the shape `NET-ADR-011` uses for `Identity`:

> "What enforces it today is not a convention but a chokepoint" (`docs/adr/NET-ADR-011-identity-and-trust.md:147-151`)

proved the same way, by a compile-fail doctest triple in the shape of `crates/ton-net-cell/src/cell/hash.rs:48` and `:62`. The third block, which must compile, exists for the reason written out at `crates/ton-net-cell/src/cell/hash.rs:88-95`: a `compile_fail` block passes on any compile error, so a block that must compile is what stops the pair going green for the wrong reason.

**The signature is verified before a sendable value exists.** Design, gated by G5. `into_signed` calls `verify` (`crates/ton-net-block/src/signature.rs:81`, public module at `crates/ton-net-block/src/lib.rs:63`) with the wallet's public key, the signing hash, and the caller's sixty-four bytes, and returns `Err` rather than a `Signed` on failure. Three properties follow, and none of them is policy:

- **A `Signed` cannot exist over a cell the caller did not sign.** So the library cannot substitute its own message after the caller approved one. Every quoted formulation of the custody sentence constrains the library's relationship to the *key*; none constrains its relationship to the *authorization*. This is the bound on that second hazard, and it is mechanical.
- The bytes on the wire are a pure function of the verified pair, because `to_boc` assembles from exactly the signed-over cell and the signature.
- **A sixty-four-byte confusion is closed by a check rather than by a name.** An Ed25519 secret is thirty-two bytes and will not compile into a `[u8; 64]` slot. But an Ed25519 keypair encoding, secret concatenated with public, *is* sixty-four bytes, and a caller who passed those where a signature belongs would have secret material serialized into a broadcast message. A naming convention does not close that. Verification inside the constructor does: keypair bytes fail `verify`, and no `Signed` is produced.
- The custody posture of `signature.rs` is unchanged. Its constant-time waiver is scoped to public inputs: "Nothing here is secret, so nothing here needs to be constant time" (`crates/ton-net-block/src/signature.rs:22-24`). All three arguments to `into_signed` are a public key, a public message, and a public signature. `NET-ADR-006`'s custody sentence widens by one word: the library now also *checks* a signature the caller presents, and still produces none.

**The library invokes nothing.** There is no callback, no trait, no closure, and no `Signer` type in this design. Sixty-four bytes cross inward and nothing crosses outward. Four consequences follow by construction rather than by rule:

- Blind signing over a digest the library chose is not a hazard to police, because the library cannot ask for a signature at all. The caller runs the operation and hands back the result.
- Implicit re-signing is unrepresentable. There is nothing to re-invoke. A retry past the signed deadline requires a new `Unsigned` and a new caller signature, which is the correct shape anyway: the deadline sits inside the signed bytes.
- The sans-I/O boundary is never crossed by the seam. `NET-ADR-002` requires that protocol logic "produces bytes to send and consumes bytes received, and nothing more" (`docs/adr/NET-ADR-002-architecture.md:48-50`). A callback would have forced a sync-or-async decision, a `Send + Sync` decision, and an unwind-across-the-seam decision. A `[u8; 64]` forces none.
- There is no key-shaped hole in any signature in the design. No parameter anywhere takes key material.

**What none of the four holds, stated as an absence rather than hedged.** They do not constrain what a caller's signer does with the cell it was handed; a signer that hashes without reading is blind-signing by its own choice, and `Unsigned::intent()` is a convenience toward the strongest signer shape rather than a mechanism enforcing it. They do not survive the FFI unchanged: `docs/api-design.md` already concedes that the Node shape convention is weaker than the Rust type guarantee, and the same weakening applies here. And `bindings/node/src/lib.rs:27` is `#![deny(unsafe_code)]` where all six core crate roots are `#![forbid(unsafe_code)]`. That gap does not close, which W0 records: the binding contains unsafe code that `napi_derive` generates and permits, so the weaker lint is the strongest one it can carry.

### 2.3 The vocabulary conflict this design creates

`NET-ADR-001` and `NET-ADR-002` describe the seam as a callback:

> "The write path first touches key material through the signer seam, where a caller supplies a callback and the library never sees a key" (`docs/adr/NET-ADR-001-purpose-and-priorities.md:107-110`)

> "the signer seam, where a caller supplies a callback and the library never sees a key" (`docs/adr/NET-ADR-002-architecture.md:139-140`)

`docs/design/system-design.md:430-431` describes it as broadcasting already-signed bytes. A value boundary matches the third description, is a fair reading of "supplies the signing operation", and **falsifies the word "callback" in the two ADRs above**. Two accepted records need an edit. That count is not reachable by grepping for the phrase `signer seam`, which returns seven files and misses this entirely, so it is recorded here explicitly. `NET-ADR-013` carries the edit.

## 3. Objections that survived

This plan builds from the staged shape rather than the two others considered. The objections that survived that choice are recorded rather than smoothed, because each one is a live risk.

**D1. Whether `Settled::Expired`, the proven negative, is sound.** It is the strongest idea in this plan, and its first phrasing was unsound at the scope asserted, on this reasoning: the verdict is computed from the masterchain head's `gen_utime`, while a wallet in workchain 0 is proven through a shard block whose own clock this tree does not decode. `ShardDescr::load` returns after `root_hash` and reads no clock at all (`crates/ton-net-block/src/shard.rs:243-249`), and the neighbouring header reader skips `gen_utime` by name (`crates/ton-net-block/src/shard.rs:217-218`). So a masterchain clock past the deadline does not by itself establish that the shard's clock was past it.

**Resolution taken here:** the feature ships, and its claim is narrowed to what the tree can compute. See item W7 and section 6. The narrowing is the whole of the resolution; the objection is correct at the scope it was raised, and a verdict phrased as "permanently dead" would be a sentence wider than the check under it.

**D2. Whether reducing this stage's capability set requires an amendment or is sequencing.** One reading holds that shipping one wallet family, no seed phrases, no hierarchical derivation, and no TON Connect proof verification is a reduction of a fixed scope statement and must be recorded as an amendment, since `NET-ADR-003:64` says the scope lists are "a boundary, not a backlog: the items on it are declined, not deferred." Another treats the same reduction as ordinary sequencing.

**Resolution taken here:** it is an amendment and `NET-ADR-013` records it as one. Question Q5 in section 4.

**D3. Whether the confirmation loop's cost is affordable.** Each confirmation poll runs a full proof walk, because `Client::account` calls `self.sync()` first (`crates/ton-net/src/client.rs:261-263`), on the one ADNL channel a `Client` owns (`crates/ton-net/src/client.rs:46-48`), for a window sized by the signed deadline.

**Resolution taken here:** the objection is accepted and answered with a count rather than a stopwatch, per `NET-ADR-012` decision 4: "A performance claim in this crate is held to an allocation count, not to a stopwatch" (`docs/adr/NET-ADR-012-scale-contract.md:304`). Item W6 makes the confirmation's proof-walk count an asserted equality against a scripted transport, and question Q6 puts the poll strategy to the ADR.

**D4. Whether re-offering the message on a poll that shows no movement is safe.** The justification first offered for it is self-defeating: it argues a liteserver drops a byte-identical duplicate before doing work, which would make the re-offer useless, while the corpus loop it was drawn from re-sends precisely because a server may have lost the message. Byte-identity is also not established at the layer needed, since `AdnlConnection::query` draws a fresh random query id and nonce per call (`crates/ton-net-adnl/src/connection.rs:142,147`) while `build_query` wraps only the inner payload (`crates/ton-net-lite/src/client.rs:159-163`).

**Resolution taken here:** v0.5.0 does not re-offer. The confirmation loop polls and does not send twice. Re-offer is a policy with a cost model this tree cannot currently measure, and it is question Q7.

**D5. Whether mnemonic and derivation belong in the library at all.** Three answers are available: permanent refusal, a pure function inside the workspace, and an isolated crate. Nothing here settles between them. **Resolution taken here:** v0.5.0 ships none of it, so the question is settled under no schedule pressure, in `NET-ADR-013`, as question Q4.

## 4. NET-ADR-013, required before any code

`NET-ADR-003` gates part of this explicitly:

> "The seed-phrase standard and the hierarchical derivation scheme are in scope as capabilities, and they are security-relevant facts. This record does not fix which mnemonic standard or which derivation scheme they use. Those are settled in a security review before that code is written, and nothing here should be read as choosing one." (`docs/adr/NET-ADR-003-scope-and-write-path.md:140-143`)

and the release sequence puts a per-change review obligation on the key-handling path (`NET-ADR-003`).

No production code in section 7 begins before `NET-ADR-013` is accepted. Section 8 is not gated on it. The record must answer the following, and two more questions raised where they arise, Q14 at section 6 and Q15 at S5. Each answer is either a decision or a stated refusal.

**Q1. Does "the library" in the custody sentence name the `ton-net` facade's dependency closure, or the repository?** This is first because it is the only question whose answer changes the crate graph, and every mechanical guarantee in section 2 is made of the crate graph. Under the v0.5.0 design the answer costs nothing, because no seed enters either scope. It costs a great deal the moment derivation is admitted anywhere, which is why it is settled now.

**Q2. Which formulation of the custody guarantee binds?** `NET-ADR-003:69-71` says "never sees"; `NET-ADR-003:133-137` says "never holds or sees". The operative decision clause carries the weaker one. The record states which binds, and edits the other to match.

**Q3. Does "seed" in the custody sentence mean a wallet seed only?** The tree already holds a seed it draws and sees: `HandshakeSecrets { key_seed: [u8; 32], .. }` (`crates/ton-net-adnl/src/handshake.rs:39-46`), consumed at `crates/ton-net-adnl/src/handshake.rs:99`, drawn from the OS at the I/O edge (`crates/ton-net-adnl/src/connection.rs:221`). It is an ephemeral transport session key and protects nothing of the user's. The sentence is nonetheless ambiguous against its own repository today, and the record disambiguates it.

**Q4. The mnemonic standard and the derivation scheme.** Four sub-questions, and the record answers all four:

- **Q4a. Which mnemonic standard.** External research establishes that the native TON scheme uses the same wordlist as BIP-39 with a different key derivation function, has **no BIP-39 checksum**, and validates a phrase by a rejection-sampling probe over a second derivation with a different salt. That probe is the only integrity check a phrase has. Getting it wrong silently accepts an invalid phrase.
- **Q4b. Which derivation scheme, and whether hierarchical derivation exists at all.** External research establishes that the native path is flat, one phrase to one keypair, with multiple accounts coming from a subwallet identifier rather than from a derivation path; that at least three mutually incompatible hierarchical schemes are in use; and that only one of them is pinned externally, by a hardware wallet rather than by the protocol. **The same words yield different keys under different schemes.** A library that guesses hands a user the wrong account silently. The record must either name one scheme, require the caller to name it explicitly with no default, or decline the capability.
- **Q4c. Where the derivation runs relative to the seam.** Verified at the scope of `docs/`: the token `mnemonic` occurs at exactly three lines in the whole repository, `docs/adr/NET-ADR-003-scope-and-write-path.md:141` and two lines of the release sequence, and none of them says where the derivation runs. A function taking words and returning a key sees a seed by definition. Q1 decides whether that is inside the line or outside it.
- **Q4d. What "settled in a security review" produces.** `NET-ADR-003:141-143` and the release sequence both require a review and name no artifact and no pass criterion. As written, no state of the world violates the requirement. The record names the artifact, gives it an id, and states the gate that refuses the first commit touching a key derivation function until that artifact exists and is accepted.

**Q5. The stage scope reduction.** `NET-ADR-003:46-48` lists "the wallet contract families, seed phrases, hierarchical derivation, and TON Connect proof verification" in the same sentence as the write path. v0.5.0 ships one family and none of the other three. `NET-ADR-003:64` fixes that "The out-of-scope list is a boundary, not a backlog: the items on it are declined, not deferred", so moving an item across the line is an amendment. The record either amends the scope statement or records that the write-path stage spans two releases and names what falls in each. It also resolves the ordering tension the release sequence records against itself: the first says this stage can follow a transaction to its result, the second puts the queries that fetch a transaction in a later stage that declares this one upstream of itself.

**Q6. The confirmation poll strategy, and its budget.** Each poll of `Client::account` runs `sync` first (`crates/ton-net/src/client.rs:261-263`). The alternative, `account_at` against a head proven once at the start (`crates/ton-net/src/client.rs:343`), is cheaper and weakens freshness in exactly the window where the chain is moving. `NET-ADR-003:79-81` refuses a proven head older than a configured bound, and `crates/ton-net/src/client.rs:29` sets `PROOF_TIMEOUT` at 60s against `CALL_TIMEOUT` at 15s (`crates/ton-net/src/client.rs:21`). The record picks, and states the bound the confirmation window is held to.

**Q7. Whether the confirmation loop may re-offer a message.** See D4. If yes, the record states the identity under which a re-offer is a duplicate and states the per-address budget it must respect. If no, it says so and the loop polls only.

**Q8. The confirmation's exact claim, and the shard clock.** See D1. The record fixes the sentence `Verified<Settled>` is allowed to carry, at the scope the tree can compute, for both the positive and the negative verdict. It states whether the negative verdict is available for a workchain-0 account at all given `crates/ton-net-block/src/shard.rs:217-218,243-245`, or whether it is available only against a masterchain-visible clock with a stated safety margin.

**Q9. Does `VERIFY_EPOCH` move?** `NET-ADR-008` fixes the trigger: it "rises only when the accept and reject boundary moves: when a new kind of proof is accepted, when an acceptance condition tightens or loosens, when the rule for validator signature weight changes, or when a freshness default changes" (`docs/adr/NET-ADR-008-versioning-and-bindings.md:56-60`). The v0.5.0 confirmation reuses the existing proven account read and adds an equality on a decoded field, so no trigger fires. The record states this rather than leaving it inferred, and gate G9 makes it checkable.

**Q10. Whether a new TL request is a wire break.** `NET-ADR-008:80` defines a wire break as "a change in the bytes exchanged with the network". Bytes never exchanged before read either way. It does not bite at `0.x`, where a minor bump already admits a break, and it bites at 1.0, because `docs/release-process.md` refuses a release that makes a break under a bump that does not admit it. The record says which of the three break kinds a new request is.

**Q11. Placement, and the crate charter.** The wallet and message modules land in `ton-net-block`, whose own doc says it "decodes only what a read or a proof needs" (`crates/ton-net-block/src/lib.rs:26-28`). That sentence becomes false. The defence is `NET-ADR-009`'s own worked example, where a trunk holds a read path and a serializer together so that "a bound the read path enforces has to be the same bound the write path and a view over the same bytes enforce" (`docs/adr/NET-ADR-009-code-structure.md:26-27`, realized at `:78-84`). The record either accepts the widened charter and rewrites that sentence, or amends `NET-ADR-009:33-36` and `NET-ADR-008:37-43` to admit a seventh crate. The seventh-crate cost may be decisive against it; the record decides.

**Q12. Does the facade re-export `BlockError`?** `crates/ton-net/src/lib.rs:150-153` records this as an open decision. The write path forces it: a consumer importing only `ton_net` cannot otherwise name the error type of the constructor that is the custody seam.

**Q13. The node binding.** `NET-ADR-002` fixes that "A binding maps values across the FFI boundary and forwards to the facade. It carries no protocol logic and no verification." (`docs/adr/NET-ADR-002-architecture.md:70-72`), and `NET-ADR-001` prioritizes the mobile consumer. No write-path binding work is scheduled in section 7. The record states whether v0.5.0 ships a Rust-only write path, or whether the binding is in the stage, and if it is in the stage, how the three-shape result distinction of section 6 survives a crossing where `docs/api-design.md` already concedes the shape convention is weaker than the Rust guarantee.

## 5. The slice, as one program

```rust
use ton_net::{Client, Coins, Config, Signature, TransferPlan, WalletV4R2};

let wallet = WalletV4R2::from_public_key(public_key);        // pure
let mut client = Client::connect(&config).await?;
client.sync().await?;

let account = client.account(&wallet.account_address()?).await?;  // Verified<Account>
let seqno = wallet.seqno(account.value())?;

let unsigned = wallet.transfer(                                    // pure: no socket, no clock
    &TransferPlan::new(dest, Coins::from_nanotons(10_000_000), seqno, valid_until)
        .with_comment("hello")?,
)?;

let signature = caller_signer.sign(unsigned.sign_over())?;         // entirely the caller's
let signed = unsigned.into_signed(Signature::from_bytes(signature))?;  // verifies, or no value

let settled = client.send(&signed).await?;                         // Verified<Settled>
```

Four of those lines compile today. `Signed` carries its own confirmation predicate, so `Client::send` takes one argument and the message cannot be separated from the test that confirms it. That single-argument shape is deliberate: a design that passed the message and the predicate as two independent arguments would reopen exactly the defect `NET-ADR-011:326-334` names as its reason for existing, a value set at one call site and read at another with the path between re-derived by hand.

## 6. Verified, ServerReported, and a third shape

`docs/api-design.md:98-132` fixes two kinds of read. A send is not a read. Forcing it into either wrapper would make the type say something slightly false, which is unacceptable in a type whose entire job is to say true things.

| shape | what it says | can become |
|---|---|---|
| `Accepted` | one server ran the message against its own current state, the contract accepted it, and it entered that server's mempool | nothing |
| `ServerReported<T>` | one server's word about a value, proof bytes carried unchecked | nothing |
| `Verified<T>` | proved against a block the client established from the pinned key block | terminal |

`Accepted` has no `value()`, no `try_map`, no `From`, and a `pub(crate)` constructor in `ton-net-lite`, matching the discipline `ServerReported::new` already keeps (`crates/ton-net-lite/src/types.rs:32`). There is no expression that turns an acknowledgement into a read. That is `NET-ADR-011:196-208`'s prescription for a novel trust status, applied one layer up.

**What a send proves: nothing about the send.** Acceptance is not inclusion. That is an external fact about liteserver behaviour, and the doc comment on `Accepted` states exactly it and nothing more.

**What `Verified<Settled>` proves, at its exact scope.** At the anchor on the wrapper, an account at the wallet's address, proven against a head this client walked to from the config's pinned key block, held a data cell whose seqno is past the value the signed body carried. So that body can never run again. **It does not prove that this body consumed the seqno.** A second body signed at the same seqno by the same key is indistinguishable to this read. Closing that gap needs a transaction matched by TEP-467 normalized hash, and the query that fetches a transaction is not in this stage.

**The negative verdict, at its exact scope.** `Settled::Expired` says: at a proven head whose `gen_utime` is past the signed deadline, the account's seqno had not moved. Because the deadline sits inside the hashed cell, the wallet contract refuses the message once its own block clock is past it, so the message is dead against every block whose clock is at or past that head's. The claim is stated against **the clock this client proved**, not against the chain in general, for the reason recorded in D1: the shard clock is not decoded in this tree (`crates/ton-net-block/src/shard.rs:217-218,243-245`). Q8 fixes the final wording. The value of the verdict survives the narrowing: every client in the reference corpus can only answer "unconfirmed, may still land", and this answers a caller's real question, which is whether a retry can double-spend.

**Default-safe naming extends without a new rule.** `docs/api-design.md:374-376` fixes that "the proven read keeps the plain name, and the unchecked read asks for itself by name". `account` / `account_reported` (`crates/ton-net/src/client.rs:261`, `:280`) becomes `send` / `send_reported`, one for one.

`Verified::new` gains a second call site. `NET-ADR-011`'s context paragraph counts the sites; that count goes stale and `NET-ADR-013` moves it.

## 7. The work, dependency ordered

Every item names its authority, its definition of done, and a gate that is a command or a compile-fail test. No item's gate is a reviewer's judgement.

### W0. The binding cannot forbid, and a check reads what it can hold instead

**Authority.** `NET-ADR-003:85-89`: "Every crate that decodes bytes from a peer denies unwrap, expect, panic, unreachable, todo, and slice indexing, and forbids unsafe code." The binding decodes nothing from a peer, so the record does not reach it; the question here is what posture it can hold at all.

**Present state.** `bindings/node/src/lib.rs:27` is `#![deny(unsafe_code)]`. All six core crate roots are `#![forbid(unsafe_code)]`.

**What this item first proposed, and why it is refused.** Moving the binding to `forbid` does not compile. `napi_derive` expands `#[napi]` into code carrying its own `#[allow(unsafe_code)]`, and a forbidden lint refuses an allowance from a macro expansion as flatly as from a hand-written attribute. The attempt produced eighteen errors, every one E0453 and every one raised inside the expansion, at `#[napi]` and `#[napi(catch_unwind)]` sites. Two facts follow. The binding contains unsafe code, written by the macro and permitted by the macro, so no phrasing of "this library forbids unsafe code" is true at the scope of the workspace. And `deny`, the strongest lint the crate can carry, is exactly the one an inner allowance defeats without a diagnostic.

**Done.** The binding keeps `deny`. `scripts/check-unsafe-posture.mjs` reads each of the six library roots for `forbid`, reads the binding root for `deny` and fails if it forbids, and reads the binding's own source text for an allowance or an unsafe block a person wrote. They are not in v0.5.0 and are named here only so their absence is not read as an oversight.

One measurement worth recording, because it corrects an assumption: a windowed reader must read the offset index to locate a cell, so the index is itself a floor under single-cell read amplification and the saving is smaller than the bag-to-cell ratio suggests. The figure is not stated here because no fixture in this tree is at the size it would be measured at, which is what S6 in a later stage delivers. And with the checksum computed over the whole slice before any cell is read (`crates/ton-net-cell/src/boc/header.rs:42-49`, on the stated ground at `:40-41`), a windowed open reads the whole bag regardless, so the improvement is zero until that record answers the checksum question.

## 9. What v0.5.0 does not reach

Stated so none of it is read in.

- **No mnemonic, no seed phrase handling, no hierarchical derivation.** Not in any crate, not feature-gated, not in a separate crate in this workspace. `NET-ADR-003:46-48` lists these as in-scope capabilities and `NET-ADR-003:64` makes moving them an amendment; Q4 and Q5 settle it. Cargo features are additive and unify across a dependency graph, so an off-by-default gate is not off for a consumer whose graph turns it on, and a conditional custody claim is not a custody claim.
- **No software signer.** Not shipped, not feature-gated, not in a `test-utils` feature. `[dev-dependencies]` do not ship; an optional regular dependency behind a feature does.
- **No key generation.** No entropy is drawn for a user key anywhere. `NET-ADR-002:48-55` requires randomness to be carried in as a value so the function stays pure.
- **No transaction following.** The release sequence says the write path can follow a transaction to its result; the queries that fetch one are a later stage which declares this one upstream of itself. No `getTransactions`, `getOneTransaction`, `listBlockTransactions`, `lookupBlock`, `runSmcMethod`, or `getConfigParams` request or response type exists in this tree today, verified by grep over the whole worktree excluding `target/` and `.git/`, which returns nothing outside this plan. `Verified<Settled>` therefore proves a seqno consumed, not a transaction executed. Q5 records the amendment.
- **No TON Connect proof verification.** Listed at `NET-ADR-003:47-48`. It is a verification capability with its own freshness model, its own domain binding question, and its own hash construction, and it shares no code with sending. It is also a new kind of proof accepted, which is a trigger for the verification epoch to rise (`NET-ADR-008:56-60`). Keeping it out is what keeps gate G9 a meaningful negative.
- **No wallet family beyond V4R2, and no operation beyond simple send.** Other families bring a second signature-packing position, an identifier that folds a network id rather than being a plain subwallet number, a send-mode rule that is a contract-level rejection rather than advice, and, for the high-throughput family, a replacement of the seqno with a bitmap that the confirmation predicate of section 6 does not describe at all.
- **No connection pool.** A `Client` owns one channel and every read takes `&mut self` (`crates/ton-net/src/client.rs:46-48`). External research establishes that a confirmation poll must reach the same server that took the send, so pooling and stickiness are in tension. That tension belongs to the pool record, and this plan records that the write path's confirmation is defined against a single channel.
- **No general `send_boc(&[u8])`.** The write path sends messages this library constructed and verified. A bytes-in path would be a distinct capability with a distinct name, never a parameter added to an existing method, per `NET-ADR-011:166-169`.
- **No node binding work is scheduled.** Q13 decides whether that is correct for the stage. Recorded here rather than discovered.
- **No verification epoch movement.** `VERIFY_EPOCH` stays 2.
- **No cell-ceiling raise.** `NET-ADR-012:541-542`.

### Standing floor, inherited not restated

The release sequence fixes that each stage "clears the same floor before it is done, so each entry below names only the check it adds." The five invariant trust properties (`NET-ADR-003:73-89`), performance within the safety floor (`NET-ADR-001:48-54`), and node-scale breadth as isolated paths (`NET-ADR-009`) apply to every item above without being restated per item. The inheritance rule is explicit: "Each new part of the surface inherits the five invariants as part of its definition of done. A part that cannot meet them is escalated under the consumer-priority guard, not shipped around them." (`NET-ADR-003:117-119`).

- **The identity between a built cell's representation hash and the hash the wallet contract computes over the body.** Every wallet family in the external corpus relies on it. It is not verified in this tree and is not asserted here. G3's byte-exact vector, taken from a real signed message rather than from a documentation page, is what establishes it. - **The two TL constructor ids** for the send request and its status response. External, pinned by G4.
- **The TEP-467 normalization rule.** External, pinned by G4.
- **The V4R2 signed-body field order.** External. The corpus contains a family whose published documentation states a field order the contract contradicts, and a shipped client carrying a comment saying so.
