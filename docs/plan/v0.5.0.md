# ton-net v0.5.0: the write path

**Status:** planned. The decisions this stage rests on are taken in section 4.
**Version at planning time:** `0.4.2` (`Cargo.toml:12`).
**Verification epoch at planning time:** `2` (`core/src/lib.rs:173`).

Every claim about this tree below carries a `file:line` anchor and states the scope it was checked at, except where the claim is about the release sequence itself, which is named rather than anchored. Anchors were first taken at `e5a6a80`, working tree clean, and re-resolved after the six library crates became one crate at `core/`: each path was mapped onto its module and each line number read out of the current file rather than carried across, since a line number from the old tree is worse than no anchor at all. Facts that live outside this repository, whether about TON contracts, liteserver internals, TL constructor ids, or what other implementations do, are marked external, listed in section 10, and not asserted here; each one is bound to a gate that turns it into a checked fact before the code that depends on it ships.

---

## 1. What v0.5.0 delivers

**The write path, as one vertical slice: build an external message, sign it outside this library, send it, and read the result back in a proven account read.**

`NET-ADR-001` fixes the target:

> "the write path, a trust-minimized read-and-send client able to back a wallet end to end, is the floor the project holds itself to" (`docs/adr/NET-ADR-001-purpose-and-priorities.md:75-78`)

and fixes what makes it observable:

> "The floor is observable: the cell engine ships every gate green, and the write path sends a real transfer observed in a proven account read." (`docs/adr/NET-ADR-001-purpose-and-priorities.md:121-122`)

That second sentence names a **read** as the proof. The proven read already exists: `Client::account` answers `Verified<Account>` (`core/src/client.rs:290`), and `Verified::new` is `pub(crate)` with one call site (`core/src/verified.rs:41`, called at `core/src/client.rs:413`). So the floor becomes observable the moment the send half can put one external message on the wire and the confirmation half can read the consequence back. That is what v0.5.0 builds.

Shipped capability:

- External message construction: `StateInit`, `CommonMsgInfo`, `ext_in_msg_info$10`, and the TEP-467 normalized external-in hash.
- One wallet family, V4R2, simple send only (`op = 0`).
- `liteServer.sendMessage` over the existing single-channel ADNL transport.
- Confirmation as a proven account read: a positive verdict when the signed seqno is consumed, and a **proven negative** verdict when the signed deadline has passed on the chain's own clock and the seqno never moved.
- A signer seam that is a value boundary: sixty-four bytes cross inward, and nothing crosses outward.

The scale debt from `NET-ADR-012` decisions 1 and 2 rides alongside as **side work**, in section 8. It is not the release, it lands in `core/src/cell/` only, and it is ordered so it never blocks the write path.

## 2. The custody position, stated first

This is a non-custodial library. The line is the product, so it is stated before the work and it is held by things a compiler or a command checks, not by a convention.

### 2.1 The line

`NET-ADR-003` stated it twice, and the two statements were not identical. Both now read the same way:

> "Its first contact with key material is a signer seam, where the caller supplies the signing operation and the library never holds or sees a private key or a seed." (`docs/adr/NET-ADR-003-scope-and-write-path.md:74-76`, decision 2)

> "it enters through a signer seam: the caller supplies the signing operation, and the library never holds or sees a private key or a seed. Constructing and broadcasting an external message is not custody. Signing with a key the library holds would be, and the library does not do that." (`docs/adr/NET-ADR-003-scope-and-write-path.md:138-142`, the custody section)

The operative decision clause carried the weaker predicate and the custody section carried the stronger one, which is what the release sequence carries too. D2 settled it on the stronger, and the operative clause was edited to match rather than the reverse.

**Under the v0.5.0 design both sentences are true verbatim, because no seed and no private key enters any crate in this workspace at any point.**

### 2.2 What holds it, mechanically

Four mechanisms. Each names the scope it covers, and each is followed by what it does not cover.

**The absent dependency edge.** This is the mechanism `NET-ADR-011` already uses for the trust barrier:

> "the enforcement is the absent dependency edge rather than anyone's diligence" (`docs/adr/NET-ADR-011-identity-and-trust.md:195-199`)

**That mechanism no longer exists, and what stands where it stood is a check that runs rather than an edge that is absent.** The six library crates are one crate, so there is no manifest left for an edge to be missing from. `scripts/check-layers.mjs` reads the source text of `core/src/{cell,tlb,proof,tl}` and refuses each of those layers naming `crate::adnl`, `crate::lite` or `crate::client`, naming `tokio` or `getrandom`, or reaching the socket, the filesystem, the process, the environment, a thread or either clock, which are the six reaches no manifest could ever have seen, because `std` needs no edge. `std::thread` is permitted under `core/src/cell/boc/`, where splitting a finalization wave across scoped threads is what the `parallel` feature buys, and that permission is written into the check rather than left as a hole in the pattern.

Read against that check, the two halves become:

- **The half that composes a signable body is held to no async runtime and no dependency-provided randomness, over the part of it the check reads.** Message construction lands in `core/src/tlb/` under D15, and that layer is on the refusal list, so `tokio` and `getrandom` are refused there by a command with an exit code. **The wallet half is read by nothing.** `scripts/check-layers.mjs` names `cell`, `tlb`, `proof` and `tl`, and no path under `core/src/client/`, so `core/src/client/wallet/`, where W4 lands, is outside every reading it performs. `docs/plan/one-crate.md` section 3 proposes covering that directory and the shipped check does not cover it, so this is a gap G2 closes rather than a property already standing.
- **The half that sends cannot name a `Cell`, and this one is stronger than the edge it replaces.** `scripts/check-layers.mjs` holds `core/src/lite/` to not naming `crate::cell`, and the same `crate::cell` reading has to find something in `core/src/tlb/` and in `core/src/proof/` in the same run. So a matcher that has quietly stopped matching fails on the present edges instead of reporting `lite` clean, which is a report a missing manifest line was never able to make.

Gate G2 asserts both, over source text rather than off `cargo metadata`, and asserts a present edge in the same reading, so an assertion whose reading matches nothing cannot pass for free. That two-reading discipline is copied from `scripts/check-default-deps.mjs` and is already the shape `scripts/check-layers.mjs` uses.

**Scope:** the four layers `scripts/check-layers.mjs` names, plus `core/src/lite/`, and the scope is narrower than a first reading of it in three ways. This does not say "no key can reach the library." Nothing here prevents a `&[u8; 32]` parameter from being added to any function anywhere. It does not reach `core/src/client/wallet/` at all, which is the previous paragraph's finding and not a detail. And it reads import text rather than a graph, so it holds what a person writes in a source file and says nothing about what a dependency of `ton-net` does inside itself.

**The chokepoint constructor.** Design, gated by G1. `Signed` has private fields and exactly one function in the workspace that returns it: `Unsigned::into_signed`. `Unsigned` likewise has exactly one: `WalletV4R2::transfer`. This is the shape `NET-ADR-011` uses for `Identity`:

> "What enforces it today is not a convention but a chokepoint" (`docs/adr/NET-ADR-011-identity-and-trust.md:153-157`)

proved the same way, by a compile-fail doctest triple in the shape of `core/src/cell/cell/hash.rs:48` and `:62`. The third block, which must compile, exists for the reason written out at `core/src/cell/cell/hash.rs:88-95`: a `compile_fail` block passes on any compile error, so a block that must compile is what stops the pair going green for the wrong reason.

**The signature is verified before a sendable value exists.** Design, gated by G5. `into_signed` calls `verify` (`core/src/proof/signature.rs:81`, public module at `core/src/proof.rs:50`) with the wallet's public key, the signing hash, and the caller's sixty-four bytes, and returns `Err` rather than a `Signed` on failure. Three properties follow, and none of them is policy:

- **A `Signed` cannot exist over a cell the caller did not sign.** So the library cannot substitute its own message after the caller approved one. Every quoted formulation of the custody sentence constrains the library's relationship to the *key*; none constrains its relationship to the *authorization*. This is the bound on that second hazard, and it is mechanical.
- The bytes on the wire are a pure function of the verified pair, because `to_boc` assembles from exactly the signed-over cell and the signature.
- **A sixty-four-byte confusion is closed by a check rather than by a name.** An Ed25519 secret is thirty-two bytes and will not compile into a `[u8; 64]` slot. But an Ed25519 keypair encoding, secret concatenated with public, *is* sixty-four bytes, and a caller who passed those where a signature belongs would have secret material serialized into a broadcast message. A naming convention does not close that. Verification inside the constructor does: keypair bytes fail `verify`, and no `Signed` is produced.
- The custody posture of `signature.rs` is unchanged. Its constant-time waiver is scoped to public inputs: "Nothing here is secret, so nothing here needs to be constant time" (`core/src/proof/signature.rs:22-24`). All three arguments to `into_signed` are a public key, a public message, and a public signature. `NET-ADR-006`'s custody sentence widens by one word: the library now also *checks* a signature the caller presents, and still produces none.

**The library invokes nothing.** There is no callback, no trait, no closure, and no `Signer` type in this design. Sixty-four bytes cross inward and nothing crosses outward. Four consequences follow by construction rather than by rule:

- Blind signing over a digest the library chose is not a hazard to police, because the library cannot ask for a signature at all. The caller runs the operation and hands back the result.
- Implicit re-signing is unrepresentable. There is nothing to re-invoke. A retry past the signed deadline requires a new `Unsigned` and a new caller signature, which is the correct shape anyway: the deadline sits inside the signed bytes.
- The sans-I/O boundary is never crossed by the seam. `NET-ADR-002` requires that protocol logic "produces bytes to send and consumes bytes received, and nothing more" (`docs/adr/NET-ADR-002-architecture.md:54-56`). A callback would have forced a sync-or-async decision, a `Send + Sync` decision, and an unwind-across-the-seam decision. A `[u8; 64]` forces none.
- There is no key-shaped hole in any signature in the design. No parameter anywhere takes key material.

**What none of the four holds, stated as an absence rather than hedged.** They do not constrain what a caller's signer does with the cell it was handed; a signer that hashes without reading is blind-signing by its own choice, and `Unsigned::intent()` is a convenience toward the strongest signer shape rather than a mechanism enforcing it. They do not survive the FFI unchanged: `docs/api-design.md` already concedes that the Node shape convention is weaker than the Rust type guarantee, and the same weakening applies here. And `bindings/node/src/lib.rs:27` is `#![deny(unsafe_code)]` where the library crate root is `#![forbid(unsafe_code)]`. That gap does not close, which W0 records: the binding contains unsafe code that `napi_derive` generates and permits, so the weaker lint is the strongest one it can carry.

### 2.3 The vocabulary this design corrected

`NET-ADR-001` and `NET-ADR-002` both described the seam as a callback, and `docs/design/system-design.md:449-450` described it as broadcasting already-signed bytes. A value boundary matches the third description and is a fair reading of "supplies the signing operation", so the word "callback" in the two records was false about the design that follows. Both were edited to say what the seam is, in this change rather than in a record of its own, and `NET-ADR-003`'s operative clause was moved from the weaker predicate to the stronger one at the same time, per D2.

That count was not reachable by grepping for the phrase `signer seam`, which returns seven files and misses the two sentences entirely, so it is recorded here rather than left to a later reader to rediscover.

## 3. Objections that survived

This plan builds from the staged shape rather than the two others considered. The objections that survived that choice, numbered O to keep them apart from the decisions of section 4, are recorded rather than smoothed, because each one is a live risk.

**O1. Whether `Settled::Expired`, the proven negative, is sound.** It is the strongest idea in this plan, and its first phrasing was unsound at the scope asserted, on this reasoning: the verdict is computed from the masterchain head's `gen_utime`, while a wallet in workchain 0 is proven through a shard block whose own clock this tree does not decode. `ShardDescr::load` returns after `root_hash` and reads no clock at all (`core/src/tlb/shard.rs:243-249`), and the neighbouring header reader skips `gen_utime` by name (`core/src/tlb/shard.rs:217-218`). So a masterchain clock past the deadline does not by itself establish that the shard's clock was past it.

**Resolution taken here:** the feature ships, and its claim is narrowed to what the tree can compute. See item W7 and section 6. The narrowing is the whole of the resolution; the objection is correct at the scope it was raised, and a verdict phrased as "permanently dead" would be a sentence wider than the check under it.

**O2. Whether reducing this stage's capability set requires an amendment or is sequencing.** One reading holds that shipping one wallet family, no seed phrases, no hierarchical derivation, and no TON Connect proof verification is a reduction of a fixed scope statement and must be recorded as an amendment, since `NET-ADR-003:69` says the scope lists are "a boundary, not a backlog: the items on it are declined, not deferred." Another treats the same reduction as ordinary sequencing.

**Resolution taken here:** it is sequencing, and D8 names what falls in this release and what falls in the next. The scope statement is not amended, because nothing on it is declined; the two items moved are dated, not dropped.

**O3. Whether the confirmation loop's cost is affordable.** Each confirmation poll runs a full proof walk, because `Client::account` calls `self.sync()` first (`core/src/client.rs:290-292`), on the one ADNL channel a `Client` owns (`core/src/client.rs:72-74`), for a window sized by the signed deadline.

**Resolution taken here:** the objection is accepted and answered with a count rather than a stopwatch, per `NET-ADR-012` decision 4: "A performance claim in this crate is held to an allocation count, not to a stopwatch" (`docs/adr/NET-ADR-012-scale-contract.md:304`). Item W6 makes the confirmation's proof-walk count an asserted equality against a scripted transport, and D9 settles the poll strategy, on a ground that turned out not to be cost.

**O4. Whether re-offering the message on a poll that shows no movement is safe.** The justification first offered for it is self-defeating: it argues a liteserver drops a byte-identical duplicate before doing work, which would make the re-offer useless, while the corpus loop it was drawn from re-sends precisely because a server may have lost the message. Byte-identity is also not established at the layer needed, since `AdnlConnection::query` draws a fresh random query id and nonce per call (`core/src/adnl/connection.rs:142,147`) while `build_query` wraps only the inner payload (`core/src/lite/client.rs:159-163`).

**Resolution taken here:** v0.5.0 does not re-offer. The confirmation loop polls and does not send twice. D10 settles it, and records the error a re-offer produces that means the opposite of what it reads as.

**O5. Whether mnemonic and derivation belong in the library at all.** Three answers were available: permanent refusal, a pure function inside the facade's closure, and a crate outside it. **Resolution taken here:** none of the three, for this release. Hierarchical derivation is declined outright in D5 of section 4, on the evidence that the same words yield different keys under different schemes and that the option which looks responsible is already shipped elsewhere and already fails. Seed-phrase import is held in D4: the third answer is the only one that preserves the custody sentence, and it costs a second published crate, which is not taken.

## 4. Decisions taken

Fifteen questions had to be settled before this code could be written. They are settled here, each with the evidence it rests on and a gate that is a command. Where a decision rests on a fact outside this repository, that fact is marked external and bound to a gate, per the rule in the header.

**D1. The custody guarantee is scoped to the `ton-net` crate's dependency closure, and is stated that way.** Not "the library" and not, loosely, "the repository". The sentence that binds is: no crate in `ton-net`'s normal-kind dependency closure holds, sees, derives, or generates a private key or a seed. That is a claim about a graph, so it is checkable off `cargo metadata`, and G2 checks it. The collapse of the six library crates into one narrows what the closure contains without changing what the sentence says: one workspace member sits in it now instead of six, and every other member of it is an external dependency, which is where the sentence always did its work.

Today the same sentence happens to be true of the whole workspace, because nothing anywhere in it derives a key. The closure is nonetheless the scope stated, because the closure is the boundary that would still mean something on the day derivation is admitted, and the workspace-wide reading is an accident of the current contents rather than a mechanism.

**What it does not cover:** the closure is a build-time fact. It says nothing about what a caller does with a key in their own process.

**D2. The stronger predicate binds: the library never *holds or sees* a private key or a seed.** `NET-ADR-003:74-76` carried the weaker "never sees" in the operative clause and `:133-137` carries the stronger one in the custody section. The stronger is the one the release sequence also carries, and it is the one a reader will hold the project to. `NET-ADR-003:74-76` is edited to match rather than the reverse, because narrowing a custody claim to the weaker of two published forms is not a thing to do quietly.

**D3. "Seed" in that sentence means user key material.** The tree already draws and sees a seed: `HandshakeSecrets { key_seed: [u8; 32], .. }` (`core/src/adnl/handshake.rs:39-46`), consumed at `:99`, drawn from the OS at `core/src/adnl/connection.rs:221`. It is an ephemeral transport session secret, it protects nothing of the user's, and it dies with the connection. The ambiguity is real against the repository as it stands, so the disambiguation is written at that site rather than left to a reader.

**D4. Seed-phrase import does not ship in v0.5.0, and the reason is a boundary that is not available rather than a difficulty in the code.**

A function taking words and returning key material sees a seed by definition. So the question was never whether the algorithm is hard, it is where such a function can sit without falsifying D1.

Inside the facade's closure it falsifies D1's sentence outright. A Cargo feature does not rescue it: features are additive and unify across a dependency graph, so a gate that is off by default is not off for a consumer whose graph turns it on, and a custody claim that holds only under one feature resolution is not a custody claim.

The one shape that preserves the sentence is a crate outside the closure, which a consumer reaches by naming it. **That shape is not taken, and the cost it was refused on has changed size without changing what it decides.** One library crate and eight npm packages move in lockstep from one commit through two toolchains that do not read each other, and the count is written into `docs/adr/NET-ADR-008-versioning-and-bindings.md`, `docs/adr/NET-ADR-009-code-structure.md`, `docs/release-process.md` and `scripts/check-versions.mjs`, which reports it in that shape when it passes. A second published crate multiplies a smaller surface than a seventh multiplied. **The decision stands, because what it rests on is the dependency closure and not the artifact count**: a crate outside the closure is the only shape that preserves D1's sentence, and it is still a published artifact whose version has to move with this one, whether it is the second or the seventh.

What has changed is the position the shape occupied. `docs/plan/one-crate.md:197-199` records it: after the merge there is no second crate to be outside the closure, because there is no second crate, so what was a publishing cost is now a placement question. That plan reopens where such a file could sit under one crate and does not answer it, and neither does this. What both leave standing is that it sits nowhere in v0.5.0.

So the capability waits for a release that can carry the boundary, rather than shipping under a sentence weakened to accommodate it. **The custody line is the product, and it is not the thing that gives way when a schedule and a boundary disagree.**

**What this does not cover:** a caller who has a phrase derives the key themselves and hands the signature to the seam, which takes a signature rather than a key and therefore never sees what they derived. Nothing here prevents that, and nothing here helps them do it correctly either, which D6 records as a cost rather than dressing up as a virtue.

**D5. Hierarchical derivation is declined outright, and this one is not a matter of timing.**

The reason is not that the feature is dangerous in general. It is that **on this chain there is nothing to be correct against.** The protocol reference fixes no derivation path and its key derivation carries no index. Every scheme in the surveyed corpus is one vendor's choice: two path strings in one client, a two-element prefix in one hardware application, and three exported constructions in one package that carry no path and no coin type at all.

The same words yield different keys under different schemes, established by re-derivation rather than by analogy: one key natively, a second at a three-element path, a third at a six-element path.

**The middle option is refused on evidence, not on taste.** "The caller names the scheme, with no default" is the answer that looks responsible. It is already implemented in the corpus, and it already fails: the alternate branch is nested inside a condition on the first path element, so a phrase that satisfies the native probe falls through to the native key with the caller's configured path never read. A caller who names the hardware scheme is handed the native key. The caller named the scheme; the library ignored them.

And the capability buys almost nothing here, because **multiple accounts on this chain do not come from a derivation path.** The subwallet identifier sits in the contract's data cell, which is inside the address preimage, so moving it moves the account with the key held fixed. That is what the corpus exposes as its multi-account surface, and it is reachable through the wallet type W4 builds.

**D6. What a later release starts from, so the reading is not repeated.**

These are external facts, established by survey and recorded here because the cost of rediscovering them is a wrong key rather than a wasted afternoon. None of them is asserted about this tree, and none is depended on by any code in this release.

- The scheme uses HMAC-SHA512 with **the phrase as the key and the password as the message**, which is the reverse of the more familiar convention. Writing it the familiar way round produces a different key from the same words.
- There is **no checksum on the phrase**. The only integrity check is a probe whose false-accept rate is one in two hundred and fifty six, and the reference's own source records that an import under a wrong password therefore succeeds one time in two hundred and fifty six.
- On the passwordless path the implementations agree byte for byte. **On the password path they do not.** Two ports diverge from the reference in incompatible directions, one by running the probe over the with-password entropy instead of the passwordless entropy, the other by collapsing a three-conjunct predicate to a single probe. Phrases exist that the reference accepts and those reject, and the reverse.
- Wordlist membership is not enforced by the reference, and is by some ports. That is a compatibility decision with a user-visible consequence rather than a detail, and it is made explicitly when the code is written, not inherited from whichever implementation was read last.

The consequence for whoever writes it: **implement the reference node's predicate, not a port of it**, and pin the password path with vectors, because a wrong password predicate does not fail loudly. It fails as an invalid phrase on words another wallet accepts.

**D7. What replaces the security-review clause when that code is written.** `NET-ADR-003:146-148` requires a review, names no artifact and no pass criterion, and as written no state of the world violates it. The replacement is a gate over vectors: published vectors reproduced byte for byte, passwordless and with a password, including one phrase the reference accepts that a diverging port rejects and one the reverse. A vector set exercising only the passwordless path does not satisfy it, because that is the path on which the implementations already agree. A requirement that cannot fail is replaced by one that can.

**D8. What v0.5.0 ships, and what it does not.** Ships: external message construction with the normalized external-in hash, one wallet family with simple send, the send request, confirmation as a proven account read with a proven negative, and the signer seam as a value boundary. Does not ship: hierarchical derivation, declined in D5; seed-phrase import, held in D4; TON Connect proof verification and transaction following, which go to a later release; a second wallet family; a connection pool; a general bytes-in send.

**D9. The confirmation loop re-syncs on every poll.** The cost objection is answered and is not what decides it. A re-syncing poll costs one masterchain-info, the proof rounds, and one account-state; a poll against a head proven once costs one account-state. The stored anchor is a key block that stays put between key blocks, so poll ten costs what poll one cost, and the difference does not grow with the poll count.

What decides it is that **`account_at` runs no freshness check at all.** Reading `core/src/client.rs:372-414` in full: no call to the freshness predicate and no read of `max_head_age`. The configured bound applies to `sync`, and to `account` through `sync`, and to nothing else on the facade. So proving a head once is not a cheaper form of the same guarantee, it is a different guarantee, one where the head's age at the first poll silently becomes its age at the last and the caller cannot see it, because `Verified` carries a block identity and a block identity has no clock in it.

**D10. The confirmation loop does not re-offer, and it must read one error as a success.** External, and a trap: the node deduplicates on a hash of the serialized query for a bounded window, and the duplicate comes back as an error whose text names it a duplicate. **That error means the first send was accepted.** A retry loop that reads it as a failure turns one successful send into a reported failure. So even though this release does not re-offer, the decoder recognizes that specific error as a benign confirmation rather than a failure, because a caller's own retry can produce it. G4 pins it.

**D11. The sentence `Settled::Expired` carries.** At a proven head whose clock is past the signed deadline, the sender's seqno had not moved past the signed value, so the message is dead against every block whose clock is at or past that head's. Stated against the clock this client proved, never against the chain in general, because the shard clock is not decoded here.

**D12. The positive verdict states its assumption inside the sentence.** The predicate is seqno consumption, which is sound for a single writer and ambiguous otherwise: a second body signed at the same seqno by the same key is indistinguishable to this read, and so is any other path that moves the seqno. Every client surveyed but one tests seqno movement alone, and one of those carries a comment conceding it. The one that does better matches the landed transaction's external-in body hash against what it sent. Matching the hash needs a transaction query this release does not carry, so **the assumption is written into the type's own sentence** rather than left implicit.

**D13. `VERIFY_EPOCH` does not move.** The send path adds no new kind of proof and changes no acceptance condition; the confirmation reuses the existing proven account read and adds an equality on a decoded field. G9 is the check, and it is the epoch transcript test left unedited: if v0.5.0 forces an edit there, the accept boundary moved and this decision is wrong.

**D14. A new request is not a wire break.** A wire break is a change in bytes already exchanged. Bytes never exchanged before read the same either way.

**D15. Message construction lands in `core/src/tlb/` and the wallet in `core/src/client/wallet/`, and the module documentation of `tlb` is rewritten to what it is.** No new crate, and no new top-level module. `core/src/tlb.rs` opens by saying the module turns the cells a liteserver returns into values a reader can use and decodes only what a read or a proof needs; a message a caller composes is neither, so that documentation moves when `message.rs` lands beside `account.rs`. The wallet goes under `client/`, where the module tree in `docs/plan/one-crate.md` section 4 places it as a submodule of the facade rather than a sibling of it at the root, and where a second contract family lands beside it without a new argument.

The structure sentence this decision used to carry is retired rather than restated. `NET-ADR-009`'s decisions 1 through 3 fixed the six-crate split and no longer describe the tree, which that record says under its own title, so there is no crate count left for this decision to stand on. What it stands on instead is the half of that record the collapse left untouched: decisions 4 through 7, where `pub(super)` is the currency a child exposes to its parent and a trunk holds the model its children share. D4 is what the refusal of a new crate cost, and D4's cost has changed size without changing what it decides.

**D16. The facade re-exports `BlockError`.** A consumer importing only `ton_net` must be able to name the error type of the constructor that is the custody seam.

**D17. The write path is Rust-only in this release.** No binding work is scheduled for it. The three-shape result distinction is weaker across the boundary, and getting that convention right for a send is its own problem.

**D18. The signer seam hands over a cell and offers a projection of it.** `Unsigned::intent()` re-parses `sign_over()` through this crate's own decoder, so no remembered field can disagree with the bytes. A stronger design would make the digest and its meaning one non-constructible value, so the library could not present bytes without their meaning. That is not what ships, and the weaker property is stated rather than implied.

**D19. The decompression door folds into the byte budget.** No separate record.

## 5. The slice, as one program

```rust
use ton_net::{Client, Coins, Config, Signature, TransferPlan, WalletV4R2};

let wallet = WalletV4R2::from_public_key(public_key);        // pure
let mut client = Client::connect(&config).await?;
client.sync().await?;

let account = client.account(&wallet.account_address()?).await?;  // Verified<Account>
let seqno = wallet.seqno(account.value())?;

let unsigned = wallet.transfer(                                    // pure: no socket, no clock
    &TransferPlan::new(dest, Coins::from_nanotons(10_000_000), seqno, valid_until)
        .with_comment("hello")?,
)?;

let signature = caller_signer.sign(unsigned.sign_over())?;         // entirely the caller's
let signed = unsigned.into_signed(Signature::from_bytes(signature))?;  // verifies, or no value

let settled = client.send(&signed).await?;                         // Verified<Settled>
```

Four of those lines compile today. `Signed` carries its own confirmation predicate, so `Client::send` takes one argument and the message cannot be separated from the test that confirms it. That single-argument shape is deliberate: a design that passed the message and the predicate as two independent arguments would reopen exactly the defect `NET-ADR-011:332-340` names as its reason for existing, a value set at one call site and read at another with the path between re-derived by hand.

## 6. Verified, ServerReported, and a third shape

`docs/api-design.md:126-160` fixes two kinds of read. A send is not a read. Forcing it into either wrapper would make the type say something slightly false, which is unacceptable in a type whose entire job is to say true things.

| shape | what it says | can become |
|---|---|---|
| `Accepted` | one server ran the message against its own current state, the contract accepted it, and it entered that server's mempool | nothing |
| `ServerReported<T>` | one server's word about a value, proof bytes carried unchecked | nothing |
| `Verified<T>` | proved against a block the client established from the pinned key block | terminal |

`Accepted` has no `value()`, no `try_map`, no `From`, and a `pub(crate)` constructor in `core/src/lite/`, matching the discipline `ServerReported::new` already keeps (`core/src/lite/types.rs:32`). `pub(crate)` reaches further than it did, because the crate is now the whole library rather than the query layer alone, so what it still holds exactly is the property that matters here: no expression outside `ton-net` mints one. There is no expression that turns an acknowledgement into a read. That is `NET-ADR-011:202-214`'s prescription for a novel trust status, applied one layer up.

**What a send proves: nothing about the send.** Acceptance is not inclusion. That is an external fact about liteserver behaviour, and the doc comment on `Accepted` states exactly it and nothing more.

**What `Verified<Settled>` proves, at its exact scope.** At the anchor on the wrapper, an account at the wallet's address, proven against a head this client walked to from the config's pinned key block, held a data cell whose seqno is past the value the signed body carried. So that body can never run again. **It does not prove that this body consumed the seqno.** A second body signed at the same seqno by the same key is indistinguishable to this read. Closing that gap needs a transaction matched by TEP-467 normalized hash, and the query that fetches a transaction is not in this stage.

**The negative verdict, at its exact scope.** `Settled::Expired` says: at a proven head whose `gen_utime` is past the signed deadline, the account's seqno had not moved. Because the deadline sits inside the hashed cell, the wallet contract refuses the message once its own block clock is past it, so the message is dead against every block whose clock is at or past that head's. The claim is stated against **the clock this client proved**, not against the chain in general, for the reason recorded in objection O1: the shard clock is not decoded in this tree (`core/src/tlb/shard.rs:217-218,243-245`). D11 fixes the wording. The value of the verdict survives the narrowing: every client in the reference corpus can only answer "unconfirmed, may still land", and this answers a caller's real question, which is whether a retry can double-spend.

**Default-safe naming extends without a new rule.** `docs/api-design.md:402-404` fixes that "the proven read keeps the plain name, and the unchecked read asks for itself by name". `account` / `account_reported` (`core/src/client.rs:290`, `:309`) becomes `send` / `send_reported`, one for one.

`Verified::new` gains a second call site. `NET-ADR-011`'s context paragraph counts the sites; that count goes stale, and the change that adds the site moves it.

### W0. The binding cannot forbid, and a check reads what it can hold instead

**Authority.** `NET-ADR-003:90-94`: "Every crate that decodes bytes from a peer denies unwrap, expect, panic, unreachable, todo, and slice indexing, and forbids unsafe code." The binding decodes nothing from a peer, so the record does not reach it; the question here is what posture it can hold at all.

**Present state.** `bindings/node/src/lib.rs:27` is `#![deny(unsafe_code)]`. The one library crate root, `core/src/lib.rs`, is `#![forbid(unsafe_code)]`. Six crate roots carried that block before the collapse and one carries it now, which narrows what the check reads without changing what it holds.

**What this item first proposed, and why it is refused.** Moving the binding to `forbid` does not compile. `napi_derive` expands `#[napi]` into code carrying its own `#[allow(unsafe_code)]`, and a forbidden lint refuses an allowance from a macro expansion as flatly as from a hand-written attribute. The attempt produced eighteen errors, every one E0453 and every one raised inside the expansion, at `#[napi]` and `#[napi(catch_unwind)]` sites. Two facts follow. The binding contains unsafe code, written by the macro and permitted by the macro, so no phrasing of "this library forbids unsafe code" is true at the scope of the workspace. And `deny`, the strongest lint the crate can carry, is exactly the one an inner allowance defeats without a diagnostic.

**Done.** The binding keeps `deny`. `scripts/check-unsafe-posture.mjs` reads the library crate root for `forbid`, reads the binding root for `deny` and fails if it forbids, and reads the binding's own source text for an allowance of the lint or an `unsafe` keyword. The two readings of the binding's source text are each proved against probes built to trip them, since a matcher that matches nothing passes an absence check for free; the attribute readings assert a presence, so a broken one fails loudly rather than passing. `docs/architecture.md` said "Every crate forbids unsafe code" and now names both things that sit outside it: the binding, and the test target that implements a global allocator, since a crate root's lint does not reach a test binary.

**Gate.** `node scripts/check-unsafe-posture.mjs`, joined to `just gate`. Graded by hand from eleven sides, none of them committed as a fixture: a clean tree passes; a plain safe function passes; an `allow` of the lint fails; an `expect` of the lint fails; an `unsafe` block fails; an `unsafe extern "C" fn` fails; an `unsafe impl` fails; an `unsafe static` fails; the same written into the build script fails; the binding set to `forbid` fails; a library crate root downgraded to `deny` fails. The shapes past a bare `unsafe fn` are graded because a reading that stops at `fn` walks past `unsafe extern "C" fn`, which is what a hand-written N-API export looks like, and this is the one crate where somebody would write one.

**Order.** No dependencies. Landed first.

### W9. Two checks the link verifier does not make

This item is not write-path work. It is here because everything the write path returns rests on the proof chain, and a survey of two independent node-grade implementations found two checks each of them makes that this tree does not.

**Authority.** `NET-ADR-006` fixes the signed form and the two-thirds rule. `NET-ADR-003:78-94` inherits every part of the surface into the five invariant trust properties.

**Present state, read at `e5a6a80`.**

- The `gen_validator_list_hash_short` cross-check is absent, and the tree says so and argues for the omission: "the shuffle is not implemented, and neither is the `gen_validator_list_hash_short` cross-check, which is the only check that does depend on order" (`core/src/proof/validators.rs:18-20`). The argument that follows is that the check is redundant against a correctly derived set, because deriving it wrongly makes the threshold unreachable or discards honest signatures, and either way live mainnet blocks stop verifying (`:22-30`).
- The signature set's own declared fields are not read. `signed_message` destructures `SignatureSet::Ordinary { .. }` (`core/src/proof/chain.rs:167`), discarding the catchain sequence number and the validator-set hash the set carries.

**What the argument covers and what it does not.** The recorded argument defends against a derivation error in this crate, and it is sound at that scope: a set derived wrongly fails loudly. It does not bind the set this crate derived to the set the destination header declares it was signed under. Those are different propositions, and only the second is what the two reference checks assert.

**Not established: whether either gap is exploitable.** The signed message binds the block. The ordinary form signs the destination's own root and file hash (`core/src/proof/chain.rs:168-169`), and the Simplex form requires the candidate to name the link's destination, so a signature set lifted from another block does not carry. No attack is claimed here, and none should be read in. What is claimed is narrower and is a fact about three trees: two independent implementations make a check this one does not, and this one's stated reason covers a different failure than the one those checks address.

**Not a live vulnerability, and the reason it is worth work anyway changed.** The discarded values are attacker-supplied and feed no branch, and the derived set comes from a block already proven, so lying about either is inert. The reference's own masterchain path confirms the order-invariance the skip rests on: it permutes a prefix with weights unchanged, and the catchain number enters only as a seed. Membership and weight, the only two things the lookup reads, are untouched by both gaps on the masterchain path, which is the only path this tree admits. No attack is established here and none should be read in.

**A third divergence, which the recorded argument does not cover, because it is about membership rather than order.** The reference reads configuration parameter 35 in preference to 34. This tree reads 34 unconditionally: `core/src/proof/validators.rs:47` declares it, and the literal 35 appears nowhere in that file. Parameter 35 carries the temporary set in force during a rotation, so a key block carrying it makes this tree derive the wrong set, miss the weight threshold, and answer `NotEnoughWeight`. That is a refusal with a misleading name, raised at the wrong layer, on live data, and indistinguishable from a hostile server.

**Done.** The parameter fix is a correctness bug and lands on its own, before the confirmation path of W6 and W7 ships, because `Verified<Settled>` is a claim resting on this chain. `gen_validator_list_hash_short` is then worth building on its own terms: it is the instrument that turns this whole class of divergence into a named, diagnosable error instead of a weight failure, and that is the argument for it rather than a security one.

**Gate.** A key block whose configuration carries parameter 35 verifies, asserted against a captured mainnet block rather than a constructed one. And a link whose declared validator-set hash disagrees with the derived set is refused by an exact `BlockError` value, in the shape the tamper battery already uses (`core/tests/chain.rs`).

**Order.** Before W6.

## 9. What v0.5.0 does not reach

Stated so none of it is read in.

- **No mnemonic, no seed-phrase import, no hierarchical derivation.** Not in any crate, not feature-gated. Hierarchical derivation is declined outright in D5, on evidence: the protocol fixes no scheme and the same words yield different keys under different schemes. Seed-phrase import is held in D4, because the only shape that preserves the custody sentence is a crate outside the facade's closure and a second published crate is not taken. A Cargo feature is not an alternative: features are additive and unify across a dependency graph, so an off-by-default gate is not off for a consumer whose graph turns it on, and a conditional custody claim is not a custody claim.
- **No software signer.** Not shipped, not feature-gated, not in a `test-utils` feature. `[dev-dependencies]` do not ship; an optional regular dependency behind a feature does.
- **No key generation.** No entropy is drawn for a user key anywhere. `NET-ADR-002:54-61` requires randomness to be carried in as a value so the function stays pure.
- **No transaction following.** The release sequence says the write path can follow a transaction to its result; the queries that fetch one are a later stage which declares this one upstream of itself. No `getTransactions`, `getOneTransaction`, `listBlockTransactions`, `lookupBlock`, `runSmcMethod`, or `getConfigParams` request or response type exists in this tree today, verified by grep over the whole worktree excluding `target/` and `.git/`, which returns nothing outside this plan. `Verified<Settled>` therefore proves a seqno consumed, not a transaction executed, which is why D12 puts the single-writer assumption inside the type's own sentence. D8 names the release each item falls in.
- **No TON Connect proof verification.** Listed at `NET-ADR-003:52-53`. It is a verification capability with its own freshness model, its own domain binding question, and its own hash construction, and it shares no code with sending. It is also a new kind of proof accepted, which is a trigger for the verification epoch to rise (`NET-ADR-008:61-65`). Keeping it out is what keeps gate G9 a meaningful negative.
- **No wallet family beyond V4R2, and no operation beyond simple send.** Other families bring a second signature-packing position, an identifier that folds a network id rather than being a plain subwallet number, a send-mode rule that is a contract-level rejection rather than advice, and, for the high-throughput family, a replacement of the seqno with a bitmap that the confirmation predicate of section 6 does not describe at all.
- **No connection pool.** A `Client` owns one channel and every read takes `&mut self` (`core/src/client.rs:72-74`). External research establishes that a confirmation poll must reach the same server that took the send, so pooling and stickiness are in tension. That tension belongs to the pool record, and this plan records that the write path's confirmation is defined against a single channel.
- **No general `send_boc(&[u8])`.** The write path sends messages this library constructed and verified. A bytes-in path would be a distinct capability with a distinct name, never a parameter added to an existing method, per `NET-ADR-011:172-175`.
- **No node binding work is scheduled.** D17 settles that the write path is Rust-only in this release. Recorded here rather than discovered.
- **No verification epoch movement.** `VERIFY_EPOCH` stays 2.
- **No cell-ceiling raise.** `NET-ADR-012:574-575`.
